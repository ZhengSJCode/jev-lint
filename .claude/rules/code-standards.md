# 代码规范

这个文件有两个读者：

- **Claude** 读全文 —— 写代码时就按它来，不用等谁检查
- **jev-guard** 只读带 `- 提问:` 的小节，把那些变成可打分的检查项

所以格式上分两层：**小节里有 `- 提问:` 的，是能被逐函数判定的检查项**；其余散文部分是约定，工具不检查（有的是因为判据闭在单个函数里闭不了，有的压根不是代码问题）。

小节标题就是规则的 id，改名等于换了一条规则。

## srp

- 标题: 违反单一职责
- 阈值: 0.65
- 提问: 这个函数体里是否同时出现了三类以上彼此无关的动作 —— 解析入参、写数据库、发网络请求、写文件、记日志、更新缓存、发消息这类，而且每一类都是它自己在直接做（不是交给已拆好的子函数）？
- 标准: 判据是**数得出几个彼此无关的动作**，不是「感觉它做了很多」。**编排函数不算**：只依次调用几个已经拆好的子功能、自己不直接碰外部系统（如 `register` 里依次 `on(...)`），它做的就是编排这一件事。

## long-function

- 标题: 函数过长
- 提问: 这个函数是否超过 30 行（含签名与闭合括号）？
- 标准: 数行数。超过 30 行说明它承担了多个职责，先拆职责，不要靠删空行凑数。**不算**：纯数据声明、长 `switch` 的每个分支只有一行 —— 那类没有可拆的职责。

## comment-restates

- 标题: 注释只复述代码
- 提问: 这个函数里的注释是否有只是把代码在做什么又用中文说了一遍的（「遍历数组」「返回结果」「设置变量」），而不是解释**为什么**要这么做、它防的是什么问题？
- 标准: 判据是「删掉这条注释，读者会少知道什么吗」。**不算**：解释约束、踩过的坑、业务规则的注释 —— 那些是代码本身表达不出来的。整段被注释掉的代码也不在这里（那是 `dead`）。

## stringly-typed

- 标题: 用自由文本判断状态
- 阈值: 0.9
- 提问: 这个函数是否靠比较字符串内容（相等、包含、前后缀、关键词、正则、标点）来判断程序状态、行为语义或控制流程，而不是读取结构化字段（明确的结果字段、类型化事件、状态机状态、枚举值）？
- 标准: 判据是「判断的依据是自由文本」。包括：对消息正文、日志、模型输出做字符串匹配来推断「成功」「失败」「正在提问」这类语义；把猜出来的语义再写回 metadata、事件类型或状态字段。**不算**：协议定义的枚举值、类型判别字段、以及语言层面的正常字符串处理（拼路径、格式化、判别文件扩展名）。

## over-wrapping

- 标题: 过度封装
- 提问: 这个函数（或它引入的类型）是否为一个简单透传包了一层 —— 为了「以后可能变」而引入了中间对象、包装类型、`kind`/`type` 判别字段，或者把上游的字符串包成对象又原样取出？
- 标准: 判据是「去掉这层封装，调用方是否更短、类型是否更直接」。**不算**：真正统一了多个实现的抽象；接口边界上必须做的形状转换（外部协议 → 内部模型）；给已有类型加语义的 branded type。

## unconstrained-input

- 标题: 输入没有约束
- 提问: 这个函数的参数里，是否有裸的原始类型实际代表着一个有格式或范围约束的领域概念（邮箱、URL、身份证、金额、端口号、ID），而函数内部又不得不自己再校验一遍它的格式？
- 标准: 判据是「约束没被类型承载住」—— 参数是 `string` / `number`，但它其实是 `Email` / `UserId` / `Port` 这类东西，于是每个拿到它的函数都得再查一遍。约束该在构造处校验**一次**，之后全链路信任那个类型（Parse, don't validate）。
  **不算**：校验的是**业务规则**而不是格式（「这个用户有没有权限」不是输入约束）；参数本来就是自由文本（用户名、备注、搜索词）；HTTP 入口这类边界适配层，把外部 JSON 收窄成领域对象本来就是它的职责。

## dead

- 标题: 注释掉的死代码
- 提问: 这个函数里是否留有注释掉的死代码？
- 标准: 注释掉的死代码、调试残留、被注释代替删除的旧实现。

## dup

- 标题: 重复代码
- 提问: 这个函数里是否有明显重复的代码块？
- 标准: 同一段逻辑在函数内重复出现，只有参数不同。

## flag-arg

- 标题: 布尔参数控制行为
- 提问: 这个函数是否有一个布尔参数，它的取值决定函数走两条完全不同的路？
- 标准: 布尔标志把两个函数硬塞进一个签名 —— 调用处写 `render(data, true)` 时，读者看不出 true 是什么意思。判据：某个参数类型是 boolean，且函数体内有以它为条件的、会走显著不同路径的分支。

## output-arg

- 标题: 通过参数返回结果
- 提问: 这个函数是否把结果写进传入的参数，而不是自己返回？
- 标准: 判据是数据流向被藏起来了 —— 调用处 `count(items, result)` 看不出 result 会被改写。函数体里有对参数（或其成员）的赋值，而函数自身返回 void 或 undefined。

## magic

- 标题: 魔法数字
- 提问: 这个函数里是否有含义不明的数字字面量，既没有常量名、紧邻处也没有说明它的来历？
- 标准: 判据是「读者说不出这个数字为什么是它」。0 / 1 / -1 这类惯用值、以及紧邻处有注释或常量名解释的，不算。

## side-effect

- 标题: 只读名字下的写副作用
- 提问: 这个函数的名字是否以 get / is / has / calc / format / to / parse 这类**只读或纯计算**的前缀开头，但函数体却修改了外部状态，或产生了写副作用（写库、发请求、改全局、改缓存）？
- 标准: 判据是**前缀**，不是「感觉名字像查询」—— 后者是主观的，实测反向。

## mixed-return

- 标题: 返回路径不一致
- 提问: 这个函数是否存在某些分支 return 了值，而另一些分支没有 return（隐式返回 undefined）？
- 标准: 所有分支都得能被枚举到。判据是调用方拿到 undefined 时无从分辨「没走到那个分支」还是「正常返回了空」—— 在 TypeScript 里它会逼出一堆 `as` 或让类型不准。

## new-dep

- 标题: 硬编码具体依赖
- 提问: 这个函数是否在函数体内部直接构造或取得某个具体的协作者（数据库、HTTP 客户端、服务实例），而不是从参数接收它？
- 标准: 判据是「这个依赖换不掉，因此这个函数没法被单独测」。

## placement

- 标题: 文件位置不合理
- 范围: 文件
- 提问: 这个文件是否被放在了与它职责不符的目录下 —— 比如具体领域的业务逻辑塞进了 utils/ common/ helpers/ 这类按技术分层的目录，或者所在目录的领域与文件内容对不上？
- 标准: 文件应放在与它职责对应的领域或功能目录下（如 order/ payment/ session/）。放在 utils/ common/ helpers/ misc/ 这类**按技术分层**的目录里、而内容又是某个具体领域的逻辑，就是位置不合理。

# 以下是写代码时的约定，工具不检查

有的是因为判据闭在单个函数里闭不了，有的压根不是代码问题。

## 别过度封装

透传就用原类型。上游要字符串就给字符串，不要为了「以后可能变」包一层对象、加一个 `kind` 字段或引入中间层。

判断标准：如果去掉这层封装，调用方更短、类型更直接，那就该去掉。

## 注释要写「为什么」

凡修改业务逻辑、控制流、并发调度、状态转换、重试恢复或兼容分支，必须在关键代码旁添加注释，说明**为什么需要该逻辑**、它解决的约束或防止的故障；禁止只复述代码执行了什么。仅有直接赋值、显然的参数透传等机械代码可以省略。

## 函数与模块

- **单一职责**：一个函数只做一件事。如果需要说成「先…然后…顺便…」，那就是两件事，拆开。模块、类同理。
- **一个函数不超过 30 行**。超了说明它承担了多个职责 —— 先拆职责，不要靠删空行凑数。
- 拆分的依据是职责边界，不是行数：行数只是超限的信号。

## TypeScript 项目风格

- ESM；相对导入保留 `.js` 扩展以兼容 `NodeNext`
- 文件名 kebab-case（如 `runtime-service.ts`）
- 优先使用明确类型与 `import type`
- 仓库未配置独立 lint 或 formatter 时，风格（缩进、引号、大小写命名）一律遵循现有文件格式，避免无关重排

## Surgical Changes

只动必须动的。不要顺手「改进」相邻代码、注释或格式；不要重构没坏的东西；匹配现有风格，即使你自己会写得不一样。发现无关的死代码，说出来，但别删。

判断标准：每一行改动都能直接追溯到这次的需求。

## Simplicity First

用最少的代码解决问题，不做投机性的东西：不写没被要求的功能，不为一次性代码抽抽象层，不加没被要求的「灵活性」或「可配置性」，不为不可能发生的场景写错误处理。

问自己：资深工程师会觉得这个写得过复杂吗？

# jev-lint

[中文文档](README.zh-CN.md)

Audit code standards function by function with TypeSafe's jev. Rules live in `rules.md`. As a Claude Code mod it reviews the files changed during a turn, once that turn ends.

## Layout

```
.claude-plugin/plugin.json   mod manifest
hooks/hooks.json             declares entry modules
hooks/register.ts            mod entry: mounts 4 hooks
hooks/check-tools.ts         registers check_file / check_snippet for the model
hooks/run-cli.ts             spawns the CLI as a child process (no Node in the sandbox)
hooks/sources/               changed-file strategies: contract + two implementations
rules.md                     rule definitions (edit takes effect on the next run)
types/claude-code.d.ts       engine type declarations (generated by /plugin-types)
tsconfig.hooks.json          type-check config for hooks

src/                         core + CLI (the mod invokes it as a child process)
  core/
    types.ts     shared types: Rule / FnSlice / Violation
    rules.ts     parses rules.md
    extract.ts   source → function slices (TS AST)
    jev.ts       TypeSafe client and questions
    check.ts     orchestration: extract → ask concurrently → filter by threshold
    env.ts       API key loading
    format.ts    report rendering
  index.ts       CLI entry
  adapters/      settings-hook adapters (alternative route)
```

## Rules live in rules.md, not in code

Rules, questions and criteria all live in `rules.md` at the project root:

```markdown
## srp

- 标题: 违反单一职责
- 提问: 这个函数是否违反单一职责——做了不止一件事，且这些事不属于同一抽象层次？
- 标准: 一个函数只做一件事。说成「先…然后…顺便…」就是两件事
```

Changes take effect **on the next run — no rebuild needed**: the file is re-read on every check. Fenced code blocks in the document are skipped, so you can put format examples at the top.

Default is **12 rules** — the list is not duplicated here; `rules.md` is the source of truth. Keeping a copy here means remembering to change both, and they will drift.

To add something like "leftover debug output", append a section to `rules.md`.

> The wording of `提问` is the criterion: asking "does this violate single responsibility" gives you the **violation** probability, while "does it do only one thing" gives the **compliance** probability. The thresholds point in opposite directions, so changing the wording means changing the thresholds too.

Rules are not shipped on the strength of a hunch — every one was checked against a **control pair** (the same problem, one case that should fire and one that should not). The results and where the two threshold lines come from are in "Thresholds" below.

## Why judge with jev instead of letting Claude look itself

Claude reviewing its own fresh code has three problems:

1. **Confirmation bias** — it just decided to write it this way, so judging "is this good" skews toward pass
2. **Unstable results** — the same code asked twice can give different answers, with no reproducible baseline
3. **No knob** — to make it stricter or looser you can only edit the prompt, and you cannot tell how wide the blast radius is

jev returns a **probability scalar**, and with two lines (error / warning) you control both "how much gets reported" and "how hard it blocks". The judgement itself is stable — measured on the same file three times in a row, the hit set came out identical (`entropy-analyzer.ts` 2/2/2 hits, `skeleton.ts` 3/3/3).

The one exception is **the case where the probability sits exactly on the threshold**: measured on `askChunk`, `srp` returned `0.50` twice in a row and then fell below the line on the third run, so 2 hits became 1. Keep the threshold at the edge of the cluster of hits, not cutting through the peak.

## Usage

### Command line

```bash
npm install
npm run build

# audit one file
node dist/index.js src/core/check.ts

# tune thresholds / emit JSON
node dist/index.js src/core/check.ts --warning 0.6 --error 0.85 --json
```

The exit code is `1` when there are **error-level** violations (warnings are printed only and do not affect the exit code) — so it drops straight into CI or a pre-commit hook.

## Using it as a Claude Code mod (recommended)

A mod is Claude Code's customization mechanism: a plugin whose behavior lives in TypeScript hook modules. This project's `.claude-plugin/plugin.json` + `hooks/register.ts` is one.

```bash
CLAUDE_CODE_ENABLE_FUNCTION_HOOKS=1 claude --plugin-dir /Volumes/Lenovo/code/jev-guard
```

It mounts four hooks across two shapes:

| hook | what it does |
|---|---|
| `session.start` | registers the `check_file` / `check_snippet` tools (the model-invoked shape) |
| `tool.call`（`Edit` / `Write` / `NotebookEdit`） | only records the edited file path — microseconds, no judgement |
| `tool.call`（`mcp__jev-lint__*`） | runs the check when the model calls one of the two tools above |
| `turn.complete` | end of turn: audits everything recorded, writes hits below that turn's answer |

**Why this is more accurate than a settings hook**: it audits **the files actually edited during this turn**. A settings hook can only guess from `git status`, so it sees every uncommitted change in the working tree — stale edits from earlier in the chat get audited too.

Three rules to avoid being a nuisance:

1. **Subagents are not audited** — if `e.agentId` has a value, pass through untouched (a subagent's edits are not charged to the main loop)
2. **No audit unless the turn answered normally** — skip when `e.reason !== 'answer'`: with interruption, refusal or error, the code is usually half-written
3. **No output when nothing hit** — the first principle is not to interrupt

### Two strategies for collecting changed files

The plugin option `fileSource` decides how "which files changed this turn" is computed:

| value | how | upside | cost |
|---|---|---|---|
| `tool-call` (default) | accumulate edit-tool calls as Claude makes them | **exact to this turn** — stale edits in the working tree are not misreported | blind to files changed via Bash (`sed -i`, `> file`) |
| `git-diff` | ask git for the working-tree diff | sees Bash edits, structurally stable | sees **all** uncommitted changes, cannot tell whether they came from this turn |

Configuration (user-level `~/.claude/settings.json`):

```json
{
  "pluginConfigs": {
    "jev-lint": {
      "options": { "fileSource": "git-diff" }
    }
  }
}
```

An unrecognized value falls back to `tool-call` rather than erroring — it is a config field, and one typo taking the whole hook down is worse than a default.

Both strategies live under `hooks/sources/`, one file each, sharing the shape defined in `contract.ts`: `observe` decides whether to record (empty for `git-diff`), `files` produces the result. A third strategy only has to implement that one interface.

> The interface **deliberately does not receive `$`**. Engine validation forbids passing `$` as a whole (verbatim: `$ itself is passed as an argument (bound, passed, spread, returned or read)`); it is only allowed at the call site as `$.noun.event(...)`. So `files()` receives a plain function already bound at the call site.

Local validation:

```bash
claude plugin validate .          # reads manifest and hooks the way the engine actually loads them, reports what would be rejected
npx tsc -p tsconfig.hooks.json    # type check
```

> ⚠️ Function hooks are **early access**; the docs say plainly that the interface may change between versions without notice.
> `types/claude-code.d.ts` is the engine's declaration file, generated by `/plugin-types` — regenerate one after upgrading Claude Code.

## Alternative: settings hook

If you would rather not enable function hooks, the classic `settings.json` route also works:

```json
{
  "hooks": {
    "Stop": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "node /Volumes/Lenovo/code/jev-guard/dist/adapters/stop.js",
            "timeout": 300
          }
        ]
      }
    ]
  }
}
```

Its changed files can only come from `git status --porcelain` (Stop's input carries no file paths, and the docs explicitly warn against parsing the transcript), so: it only works inside a git repo, it sees all uncommitted changes, and it skips when more than 20 files are involved.

`decision`/`reason` are **top-level** fields; putting them inside `hookSpecificOutput` is silently ignored.

To get feedback on every file edit, swap `Stop` for `PostToolUse` + `matcher: "Edit|Write"` + `dist/adapters/hook.js` (at the cost of one model call per file):

> ⚠️ Under PostToolUse **plain-text stdout on exit 0 goes only to the debug log** — Claude never sees it
> (the allowlist of exceptions that reach context is just `UserPromptSubmit`, `SessionStart` and those few). It has to be wrapped in
> `hookSpecificOutput.additionalContext`.

## Thresholds: two levels, error / warning

The score decides everything; the rules themselves do not move. Two lines:

| level | default line | meaning | evidence |
|---|---|---|---|
| **error** | ≥ `0.9` | **must fix** — the CLI returns non-zero, so it can block CI | above 0.9 there are **only true hits** |
| **warning** | ≥ `0.7` | worth a look — listed only, blocks nothing | below 0.7 is noise; 0.7–0.9 is "worth a glance" |

Below the warning line nothing is reported at all.

**Each rule can also carry its own line** (write `- 阈值: 0.9` in `rules.md`), overriding the global warning line. This is not optional — measured distributions differ widely per rule:

| rule | true hits | false positives | line set for it |
|---|---|---|---|
| `srp` | 0.69 ~ 0.87 | 0.05 ~ 0.15 (orchestration functions) | **0.65** |
| `stringly-typed` | 0.96 | 0.74 ~ 0.88 (legitimate string handling) | **0.9** |
| the rest | — | — | global 0.7 |

One global line cannot separate these two families: set it to 0.9 for `stringly-typed` and `srp`'s true hits are missed; set it to 0.65 for `srp` and all of `stringly-typed`'s false positives come in.

**Why the exit code only looks at error**: using warnings to block CI trains everyone to ignore warnings — that is exactly what the two levels are for. On one project: threshold 0.5 reported 18 items (almost all noise), 0.9 reported 1 (a true hit).

```bash
node dist/index.js src/foo.ts --warning 0.6 --error 0.85
```

### Don't lower false positives by editing rules

Been there. The lesson: it turns general industry rules into an ever-growing set of special cases ("`fs`/`process` don't count", "factory functions don't count", "print width doesn't count"…), and each rule's best threshold differs anyway, so you end up with no single knob.

**Every trade-off between false positives and misses goes to these two lines.**

The only exception is **when the criterion itself is not judgeable** — then what has to change is not the wording but whether the rule lives:

| symptom | example | disposition |
|---|---|---|
| you need the caller to tell | `swallow` (swallowed exception): whether the error is handled after degrading is invisible inside the function | **delete the rule** (a note is kept in `rules.md`) |
| the criterion is a subjective impression | `side-effect` originally asked whether the name **suggests** read-only; counterexample `syncUser` scored 0.88 | **switch to an enumerable criterion** — change it to "is the prefix `get`/`calc`", same sample set scored 0.96 against 0.03 |

### Which rules were validated

Every one was checked against a **control pair** (the same problem, one case that should fire and one that should not) — except `dead` / `dup`, the two earliest rules, which never got a control pair of their own and so are absent from the table below:

| rule | control result | conclusion |
|---|---|---|
| `flag-arg` | 0.97 vs 0.04 | reliable |
| `output-arg` | 0.98 vs 0.01 | reliable |
| `new-dep` | 0.98 vs 0.02 | reliable |
| `side-effect` | 0.96/0.94 vs 0.03/0.02/0.10 | reliable (the criterion must use the prefix) |
| `mixed-return` | 0.95 vs 0.11 | reliable |
| `magic` | 0.93 vs 0.37 | reliable |
| `srp` | 0.87 vs 0.18 | usable, but reports too many false positives on real projects (orchestration functions read as multi-responsibility) |
| `placement` | ① 0.92 vs 0.04 ② two real projects | reliable: 40 domain-directory files in marauder, **0 reports**; 23 files in vscode-hide-comments, 7 reported and **all under `utils/`** |
| `swallow` | empty `catch` judged compliant, an explained one judged violating | **unreliable, deleted** |

**Self-check before writing a new rule**: is everything needed to judge it inside this one function? Move the function as-is to another call site — does the conclusion flip? If it flips, it does not belong here — that is how `swallow` was stopped.

## Known limitations

- **TS/JS only**. Python's AST is incompatible with the TS parser; supporting it means writing another `extract`
- **One request per function**. A 20-function file is 20 calls; at concurrency 4 that is about 4 seconds — noticeably slow on large files
- **No fix suggestions**. jev only answers a probability scalar and has no ability to give code-level advice; the report will not invent boilerplate posing as its opinion
- **Anonymous callbacks are not audited**. Nested callbacks like `arr.map(x => ...)` do not become slices of their own; the responsibility lives in the top-level functions and class methods

The core (`core/`) depends on nothing from Claude Code. To move to an MCP server, a skill or another editor's plugin, swap a thin adapter layer.
